# PM 세션

> **작업 세션은 이 파일을 읽지 마라.** PM 전용이다.
> 작업 세션이 스스로 발견해야 할 것이 들어 있다. 미리 읽으면 관찰이 아니라 받아쓰기가 된다.

## 새 PM 세션 개시 프롬프트 (복붙)

```
너는 Claro 프로젝트의 PM 세션이다. 구현은 하지 않는다.

읽을 것 (이 순서로):
  CLAUDE.md
  docs/PM.md            ← 이 파일. §1 지금 상태 → §2 일하는 방식 → §3 검수 도구 → §5 교훈
  docs/DECISIONS.md     ← 표만 먼저. 본문은 필요할 때
  docs/development-backend.md · development-frontend.md · development-content.md  ← 각 레인 맨 위 "현재 위치"와 Step 표

docs/FINDINGS.md 는 통째로 읽지 마라 (43KB). 필요한 절만 그때그때.

다 읽었으면 도윤에게 §1 을 세 줄로 요약해 보여주고,
"프롬프트를 넘겼는데 결과가 안 온 세션"이 실제로 돌고 있는지 확인받아라.
문서에 없는 진행이 있을 수 있다.
```

# 2. 일하는 방식

## 루프
```
도윤이 작업 세션 보고를 붙여 넣는다
 → PM 재현: 커밋·push 확인, 검사 스크립트를 직접 다시 돌린다 (§3). 보고를 그대로 믿지 않는다
 → PM 원문 대조: 산출물을 열어 판정·수치를 실물과 대조한다. 스크린샷은 직접 본다
 → 분류: DECISIONS 로 / 다음 세션으로 / 폐기
 → 기록: DECISIONS · development-*.md · 이 파일. 판단을 대화에만 남기지 않는다
 → 후속 지시문 또는 다음 프롬프트를 써서 도윤에게 준다 (복붙 가능한 코드 블록)
 → 도윤이 세션에 전달
```

## 게이트 — 누가 판정하나
- 도윤은 판정을 **PM 에게 위임**해 왔다 (D19 · D20 · D22 · D23 · D25). 그 경우 DECISIONS 에 "PM 판정 (도윤 위임)"
- 판단 순서 (도윤 지정): **① 서비스 본질 — 독자가 느끼는 것 ② 기술적 무리 · 유지보수 · 병목 회피, 적당한 지점**.
  auto-memory `decision-priority` 에도 있다
- **독자 글이 바뀌는 것 · 문안 선택은 도윤에게 올린다.** 추천을 달고 "이 메시지를 보내면 그게 승인"으로 준다 (C-1b · D23 #16)
- 독자 글이 안 바뀌는 단계는 PM 검수로 닫는다 (0.1b · F-1)

## 도윤과 말하는 법
- 한국어. 결론 먼저. 도윤이 "쉽게" / "대답만"이라 하면 그 형식으로
- 도윤은 **다른 곳의 검토 의견**을 붙여 오곤 한다. 대부분 날카롭다. 맞으면 바로 인정하고 반영한다. 틀린 곳이 있으면 근거를 대고 말한다
- PM 이 틀렸으면 한 문장으로 인정하고 고친다. 길게 사과하지 않는다

## 커밋 규칙
- **같은 작업 트리에서 다른 세션이 동시에 일한다.** `git add -A` 금지. 파일을 하나씩 지정한다
- 커밋 전 `git status` 로 남의 미커밋 파일을 확인하고 건드리지 않는다
- 커밋 뒤 push. 메시지 끝에 attribution 줄 (시스템 안내를 따른다)

## 프롬프트 쓰는 법 (지금까지 효과 있던 것)
- "읽을 것 (이것만)" — 목록을 닫는다. **그 작업이 닿는 FINDINGS 절을 빠짐없이** (S3 가 §9 를 못 봐서 어긋날 뻔했다)
- "하지 말 것" — 범위를 막는다. 특히 계약 · 골든 · 남의 레인
- 판단이 필요하면 **멈추고 `_open` 으로** — 세션이 스스로 정하지 않게
- 완료 조건에 **검증 스크립트 + 일부러 망가뜨린 사본** — 검사가 진짜 실패하는지
- 프롬프트는 **입력이 확정된 뒤에** 쓴다 (D10). 미리 쓰면 모르는 걸 가정한다

# 5. 교훈 — PM 이 반복한 실수

1. **실물 없이 계약 내용을 설계하고 "확인할 사항"으로 넘기기** (2026-09-20, 두 번: D8 `open_while`, D12 render).
   세션이 PM 추론을 전제로 작업한다 → 추론이 생기면 DECISIONS 에 OPEN 으로 내리고 세션이 실물로 답하게 한다
2. **프롬프트의 숨은 전제** (2026-09-21). "라이브러리 문안을 가져다 써라" — 라이브러리가 검증된 적이 없었다. 골든에 모순이 생겼다
   → "이 자료를 믿고 써라"를 넣기 전에 그 자료가 검증된 적 있는지 본다
3. **도윤이 세션에 직접 준 지시를 모르고 추가 지시** (2026-09-21, S2). 세션이 충돌을 감지해 멈췄다
   → 추가 지시를 쓰기 전에 세션이 이미 뭘 받았는지 확인한다
4. **자기 지시의 산물을 세상 증거로** (2026-09-28). "블록 재사용률 0%"는 PM 이 S1 에 준 "둘로 보이면 둘로 남겨라"의 결과였다
   → 세션 산출물의 숫자를 근거로 쓰기 전에 그게 PM 지시에서 나온 건지 본다
5. **프레임이 사각지대를 만든다** (2026-09-28). "시각은 정보가 아니라 모양을 더한다"를 원칙으로 두면 아무도 검사 안 한다.
   반대 방향(시각이 텍스트에 없는 주장을 더함)이 안 보인다 → D14 규칙 3
6. **읽기 목록 누락** (2026-09-29, S3 에 §9 안 줌) → 그 계약이 닿는 FINDINGS 절을 빠짐없이
7. **두 축을 하나로 합치기** (2026-09-29, 하루 세 번): 유형 ↔ 발견 검사 / 출처 커버리지 ↔ 층 (D22 · D23)
   → 규칙을 만들 때 입력 분류와 출력 분류가 같은 축인지 먼저 본다. 세션이 붙인 분류(partial · unsupported · kind)를 그대로 결정 입력으로 쓸 때 특히
8. **"전부 해소" 같은 과대 약속** (2026-09-30). "0.2b 에서 대기 13 전부 해소"라고 적었는데 계약으로 풀리는 건 3뿐이었다
   → 무엇이 계약 작업이고 무엇이 콘텐츠 작업인지 먼저 가른다
