## D8 · volatility 를 2값에서 3값으로

**상태**: DECIDED · 2026-09-20
**배경**: FINDINGS §5.4는 `STABLE | VOLATILE` 2값. 픽스처에 "이란 전쟁 201일째"를
넣으려 하자 둘 중 어디에도 안 맞는다는 게 드러났다.

### 결정
```
STABLE     안 변함                        3.75~4.00%
DERIVED    STABLE fact에서 계산됨          201일째
VOLATILE   조회해야만 알 수 있음           48건 → as_of 필수
```

**규칙**
1. DERIVED 는 `published_at` 기준으로만 계산한다. `now()` 재계산 금지 —
   같은 ArticlePackage 가 읽는 시점마다 다른 값을 보이면 immutable 이 아니다 (§9.2 위반)
2. 따라서 **렌더 시점 계산은 없다.** 프론트는 `value_at_authoring` 을 출력한다.
   공식은 발행 시 1회 검증용으로만 존재한다
3. `recompute(published_at) == value_at_authoring` 은 회귀 테스트가 아니라 **불변식**이다.
   안 맞으면 즉시 실패
4. 전파: 소스 중 하나라도 VOLATILE 이면 DERIVED 를 쓸 수 없다. VOLATILE 로 강등
5. 유효성("아직 진행 중인가")은 Fact 의 속성이 아니다. `storyline_ref` 가 답하고,
   §6.2 `STORYLINE_STALE` 이 이미 담당한다

### 기각된 안
- `derived_from.open_while` — `storyline_ref` 를 다른 이름으로 중복 정의한 것.
  Fact 스키마에 storyline 생명주기를 밀어넣는다
- `now()` 재계산 / 열림·닫힘에 따른 시계 분기 — immutable 위반. 복잡도 3배인데
  해결하려는 문제는 storyline 장치가 이미 풀고 있다

### 미해결로 남긴 것
- `derived_from` 의 정확한 필드 구조 → S3
- `render` 어휘의 소속 → **D12 참조. PM 추론을 전제로 넘기지 않는다**

### invalid fixture
- `volatile-missing-asof.json` (S2) · `derived-from-volatile.json` (S2)
- `merged-without-target.json` (S4) · `conflicting-alias-collapse.json` (S4)
  → 아래 둘은 CONCEPT_IDENTITY 가 없으면 쓸 수 없다. S2 에 주지 마라

### 메타
스키마를 먼저 만들었으면 마이그레이션이었을 것을, 픽스처를 쓰려다 발견했다.
Step 0.0(픽스처 선행) 결정의 첫 실증 사례.

## D9 · 골든 픽스처에 알려진 결함을 남기지 않는다

**상태**: DECIDED · 2026-09-20

골든 픽스처는 (a) 프론트 렌더 대상 (b) 파이프라인 diff 대상 (c) 계약 도출 원천
셋 다 "이게 정답"을 전제한다. 알려진 위반을 남기면 파이프라인이 같은 위반을 했을 때
diff 가 "일치"라고 말한다. 결함이 정답의 정의가 된다.

→ 골든은 깨끗하게. 위반 데이터는 `fixtures/invalid/` 에 별도 파일로.
→ 스키마 Task 완료 조건인 "제약 위반 데이터가 거부되는지"가 이것으로 검증된다.

| 축 | 사례 | 프로토타입 | 고유 블록 |

**유일한 예외**: FOMC 입문 3장 gauge. `left:33%`("2%") · `left:62%`("3%대") 가
inline style 에 손으로 박힌 상수다. 축 최소·최대가 선언돼 있지 않다.
선형 가정 시 62% 는 약 3.7% 를 가리키는데 본문은 "3%대"라고만 쓴다.

→ D8 의 "프론트는 `value_at_authoring` 만 출력한다"가 실물로 뒷받침된다.

## D14 · 블록 타입 — 원형 층 + 모든 블록에 정규 텍스트

**상태**: DECIDED · 2026-09-28

### 결정
골격은 닫고, 나머지는 **원형 층**에서 정의하며, **모든 블록은 정규 텍스트를 갖는다.**

처음엔 A(닫기) / B(열기) / C(골격 닫고 나머지 열되 글자 대체본 필수)의 셋 중 고르는 문제로 올렸다.
대등한 선택지가 아니었다. 정규 텍스트가 전제가 되면 C 가 B 의 문제(못 그림)를 풀고,
A 는 C 에서 확장성만 뺀 것이 된다. **실제로 정할 것은 "원형을 몇 개로 잡을까"이고, 그건 S3 가 실물에서 도출한다.**

### 근거로 쓰면 안 되는 것
**"재사용률 0%"는 증거가 아니다.** S1 프롬프트("둘로 보이면 둘로 남겨라")가 최대 분할을 보장했다.
0% 는 그 지시가 제대로 작동했다는 뜻이지, 블록이 기사마다 다를 수밖에 없다는 뜻이 아니다.
(PM 이 자기 지시의 산물을 세상에 대한 증거로 썼다)

### 원형 층 — 참고안. S3 가 확정한다
| 관측 타입 | 원형 | 근거 기사 |
|---|---|---|
| votes · tags_inline | 나란히 비교 | **FOMC + FTC** |
| timeline · steps | 순서 목록 | **FOMC + FTC** |
| gauge | 척도 (목표 대비 현재) | FOMC 만 |
| stats | 이름-값 | FOMC 만 |
| callout | 강조 문단 | FOMC 만 |
| examples | 순서 없는 목록 | FTC 만 |
| rule_line | 극성 목록 (✕/✓) | FTC 만 |

- 두 기사 모두에 근거가 있는 원형은 **둘뿐**이다. 나머지는 근거 1건이다.
  FINDINGS §13: "두 번째 구현체가 없을 때 설계한 인터페이스는 거의 반드시 틀린다"
- 스크루웜 브리프를 대보면 극성·순서·비교·이름-값으로 대부분 표현되고, 새로 필요한 건 지도(북상 경로)
  하나로 보인다. **슬라이드가 없어 검증은 안 됐다** (D11)

### 정규 텍스트는 비용이 아니라 요구사항이다
1. 프론트가 모르는 타입이 왔을 때
2. 스크린리더 — 게이지는 소리로 못 읽는다
3. 자유 질문(§10.6) — LLM 은 게이지를 못 본다. **텍스트 없는 블록은 질문 기능에 투명하다**
4. 공유·검색 — 카톡으로 나가는 건 텍스트다
5. **검증** — 원문 대조, entailment, 레드팀, 게이트 전부 텍스트에서 돈다. **텍스트 없는 블록은 QA 밖에 놓인다**

### 규칙
1. 모든 블록은 정규 텍스트를 가진다. 옵션이 아니다
2. 극성·순서·강조처럼 의미를 가진 표시는 정규 텍스트에 **글자로** 살아 있어야 한다
   — 근거: FTC 대조선. ✕/✓ 를 빼면 "금지하라 / 숨기지 마라"만 남아 어느 쪽이 되고 안 되는지 사라진다
3. **시각 블록은 정규 텍스트가 말하지 않는 것을 말할 수 없다**
4. 블록당 정답 표현은 하나다. 시각 데이터와 텍스트를 **둘 다 독립 저장하지 않는다.**
   따로 두면 한쪽만 고치는 순간 조용히 어긋난다(화면엔 3.4%, 질문 기능엔 3.3%).
   어느 쪽을 정답으로 할지는 S3 가 실물을 보고 정한다

### 규칙 3 이 핵심인 이유
PM 가설은 "비텍스트 블록은 정보가 아니라 모양을 더한다"였다. 대부분 맞다.
그러나 이걸 원칙으로 두면 **"모양일 뿐"이니 아무도 검사하지 않는다.**
더 위험한 건 반대 방향 — **시각이 텍스트에 없는 주장을 더하는 경우**이고, 프로토타입에 이미 있다.

| 블록 | 텍스트가 말하는 것 | 시각이 추가로 말하는 것 | 판정 |
|---|---|---|---|
| 게이지 | 2%, 3%대 | 눈금 33%·62% — "목표와 현재 사이 거리가 이만큼"이라는 비율. **위치에 근거가 없다** | **위반** |
| 타임라인 | 날짜 5개 | 등간격. 실제로는 9일·21일. 관례상 비례로 안 읽을 수도 있다 | 게이트 판단 |
| 수치표 | PCE 3.7% (3월 2.7%) | 빨간색 — "나쁘게 올랐다". 편집 판단이 표현에 묻혀 있다 | 게이트 판단 |

관찰은 S1·S2 가 이미 했다(FOMC-9·14·22, S2 범위 밖 #7). 그러나 전부 "프론트가 계산하느냐",
"의미냐 표시냐"로만 다뤄졌다. PM 은 D12 에서 타임라인 등간격을 **안심할 결과로** 적었다.

FINDINGS §7.8 "아직 못 잡는 것: 비유가 만드는 그림"과 **같은 범주**다. 사실 문장이 아니어서
entailment 에도 원문 대조에도 안 걸리는데, 독자 머릿속 그림은 바꾼다.
→ **게이트 3 확인 항목으로 추가.** 사람이 본다.

### 골든에 들어 있는 위반 — 게이지
입문 3장 게이지 눈금 `[33, 62]`. **S2 는 재개하지 않는다.** 고치는 방법(실제 값에서 위치 계산 /
척도를 버리고 두 값 비교로 교체)이 척도 원형을 어떻게 정의하느냐에 달려 있어서, 지금 고치면 계약을 추측하게 된다.
→ **Step 0.1b** (골든을 계약에 맞춰 재작성)에서 처리. 어느 쪽으로 고칠지는 편집 판단이라 도윤이 고른다.

D9("골든에 알려진 위반을 남기지 마라")와 긴장이 있다. 지금 골든을 읽는 건 S3 뿐이고 S3 에 명시했다.
프론트는 0.1b 전까지 열지 않는다(아래). 그래서 이 기간에 위반이 퍼질 경로가 없다.

### 순서 변경 — 프론트 레인 해제 조건 0.0b → 0.1b
원형 층으로 가면 블록 타입이 바뀌고, 블록 타입이 바뀌면 프론트 컴포넌트가 바뀐다.
"프론트는 계약이 아니라 픽스처에서 해제된다"는 **픽스처 모양이 최종이라는 전제**였다. 이제 아니다.
지금 열면 관측 타입(gauge, votes …)으로 컴포넌트를 만들고 0.1b 에서 갈아엎는다.

## D15 · `resolves` 를 데이터로 두지 않는다

**상태**: DECIDED · 2026-09-21

### 불변식
```
읽기 흐름은 선형이다.
각 슬라이드의 open_question 은 바로 다음 슬라이드가 답한다.
비선형 참조는 허용하지 않는다.
```

**"허용하지 않는다"가 핵심이다.** 비선형이 필요해 보이는 상황은 슬라이드 순서가
틀렸다는 신호다. 세 장 뒤가 답해야 할 것 같으면 순서를 잘못 짠 것이지 필드가 필요한
게 아니다. §8.1 "기사 = 하나의 모험"과도 맞다. 모험은 앞으로 가지 뒤를 참조하지 않는다.

### 근거
§8.2 가 잡으려는 것은 두 가지다.

| 잡으려는 것 | 필드 없이 | 필드 있으면 |
|---|---|---|
| open_question 없는 슬라이드 (넘길 이유 없음 → 앞뒤와 합쳐야 함) | **잡힌다.** `open_question == null` | 똑같이 잡힌다 |
| 답 없이 끝나는 질문 (독자를 버려둠) | 못 잡는다 | **여전히 못 잡는다** |

`resolves: 4` 는 4번이 답했다고 **주장**할 뿐이다. 실물 20장 전부 `index+1` 이므로 그 주장은
자동 생성이고, 자동 생성된 주장을 검사하는 것은 아무것도 검사하지 않는 것이다.

**잡히는 건 필드 없이 잡히고, 필드가 필요한 건 필드로도 못 잡는다.**

### QA
1. 마지막 제외 모든 슬라이드에 `open_question` 이 있는가 — **기계 검사**
2. 다음 슬라이드가 그 질문에 실제로 답했는가 — **의미 판정. 자동화하지 않는다.**
   게이트 3(최종 검토)에 붙인다. 슬라이드를 읽으며 "여기서 왜 안 넘어가지?"를
   느끼는 것이 가장 정확하다

### 재개 조건
비선형 참조가 **정당하게** 필요한 실사례가 나오면 재논의한다.
"순서를 바꾸면 해결되는가"를 먼저 확인하고, 안 되는 경우만 해당한다.

### 기각된 안
- `resolves` 필드 — 위 근거
- 불변식을 "open_question 은 다음 슬라이드가 답한다"로만 쓰는 안 — 약하다.
  나중에 누가 `resolves` 를 다시 제안할 때 막을 근거가 없다

## D16 · `open_question` 은 teaser 에서만 나온다

**상태**: DECIDED · 2026-09-21 · S1 FOMC-13 해소

S1 이 "한 슬라이드에 질문이 둘"인 경우를 두 건 찾았다. 정의가 없어서 둘 다 질문으로
보인 것이고, 기능이 다르다.

| | 답이 나오는 곳 | 성격 |
|---|---|---|
| **본문 수사의문문** — "이상하죠. 왜 올렸을까요?" | **그 슬라이드 안** | 리듬 장치. Writing Layer |
| **teaser** — "연준은 뭘 보고 있는 걸까요?" | **다음 슬라이드** | 넘기는 장치. 구조 |

→ **세는 것은 teaser 뿐이다.** 본문 수사의문문은 그냥 본문이고 별도 필드가 없다.
→ 이렇게 정의하면 §8.2 "질문이 정확히 하나"가 깨지지 않는다.

**미해결로 남는 것**: teaser 의 **형태**(입문 `Q …?` 질문형 / 숙련 `· 명사구` 목차형)는
별개 문제다. FOMC-3 으로 S3 에 남아 있다.

## D17 · `open_question` 은 슬라이드 사이의 독립 데이터다

**상태**: DECIDED · 2026-09-21 · **S3 가 계약을 쓸 때의 제약**

teaser 를 별도 슬라이드로 뺄 가능성이 있다. 디자인은 나중에 정한다.
그러나 계약은 지금 그 가능성을 열어둬야 한다.

→ S3 는 `open_question` 을 **"슬라이드 하단 문구"가 아니라 "슬라이드 사이의 독립 데이터"**로 정의한다.
  하단 문구로 정의하면 슬라이드의 속성이 되고, 표현 방식을 바꿀 때 계약이 바뀐다.

**기존 결정과의 관계**
- D13(슬라이드/블록 2층)은 **프로토타입 관찰**로서 유효하다. 프로토타입에서 teaser 는
  슬라이드 안에 있었다. D17 은 그걸 **계약에서 어떻게 모델링하느냐**다
- D15 불변식은 그대로 성립한다. "슬라이드 N 의 open_question" 이
  "슬라이드 N 과 N+1 사이의 open_question" 으로 읽히면 된다. QA① 도 같은 뜻이 된다
- D16(teaser 만 센다)은 그대로다

세부 UI(kicker·teaser 글자 크기 등)는 프론트 레인이 열리면 도윤이 전달한다.

## D18 · 질문 슬라이드를 PRE probe 자리로 쓸 것인가

**상태**: OPEN · 2026-09-21

D17 에 따라 질문이 별도 슬라이드가 되면, 그 자리가 설명 **전** 선행지식을 재는
