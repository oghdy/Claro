## D8 · volatility 를 2값에서 3값으로

**상태**: DECIDED · 2026-09-20
**배경**: FINDINGS §5.4는 `STABLE | VOLATILE` 2값. 픽스처에 "이란 전쟁 201일째"를
넣으려 하자 둘 중 어디에도 안 맞는다는 게 드러났다.

### 결정
```
STABLE     안 변함                        3.75~4.00%
DERIVED    STABLE fact에서 계산됨          201일째
VOLATILE   조회해야만 알 수 있음           48건 → as_of 필수
```

**규칙**
1. DERIVED 는 `published_at` 기준으로만 계산한다. `now()` 재계산 금지 —
   같은 ArticlePackage 가 읽는 시점마다 다른 값을 보이면 immutable 이 아니다 (§9.2 위반)
2. 따라서 **렌더 시점 계산은 없다.** 프론트는 `value_at_authoring` 을 출력한다.
   공식은 발행 시 1회 검증용으로만 존재한다
3. `recompute(published_at) == value_at_authoring` 은 회귀 테스트가 아니라 **불변식**이다.
   안 맞으면 즉시 실패
4. 전파: 소스 중 하나라도 VOLATILE 이면 DERIVED 를 쓸 수 없다. VOLATILE 로 강등
5. 유효성("아직 진행 중인가")은 Fact 의 속성이 아니다. `storyline_ref` 가 답하고,
   §6.2 `STORYLINE_STALE` 이 이미 담당한다

### 기각된 안
- `derived_from.open_while` — `storyline_ref` 를 다른 이름으로 중복 정의한 것.
  Fact 스키마에 storyline 생명주기를 밀어넣는다
- `now()` 재계산 / 열림·닫힘에 따른 시계 분기 — immutable 위반. 복잡도 3배인데
  해결하려는 문제는 storyline 장치가 이미 풀고 있다

### 미해결로 남긴 것
- `derived_from` 의 정확한 필드 구조 → S3
- `render` 어휘의 소속 → **D12 참조. PM 추론을 전제로 넘기지 않는다**

### invalid fixture
- `volatile-missing-asof.json` (S2) · `derived-from-volatile.json` (S2)
- `merged-without-target.json` (S4) · `conflicting-alias-collapse.json` (S4)
  → 아래 둘은 CONCEPT_IDENTITY 가 없으면 쓸 수 없다. S2 에 주지 마라

### 메타
스키마를 먼저 만들었으면 마이그레이션이었을 것을, 픽스처를 쓰려다 발견했다.
Step 0.0(픽스처 선행) 결정의 첫 실증 사례.

선형 가정 시 62% 는 약 3.7% 를 가리키는데 본문은 "3%대"라고만 쓴다.

## D14 · 블록 타입 — 원형 층 + 모든 블록에 정규 텍스트

**상태**: DECIDED · 2026-09-28

### 결정
골격은 닫고, 나머지는 **원형 층**에서 정의하며, **모든 블록은 정규 텍스트를 갖는다.**

처음엔 A(닫기) / B(열기) / C(골격 닫고 나머지 열되 글자 대체본 필수)의 셋 중 고르는 문제로 올렸다.
대등한 선택지가 아니었다. 정규 텍스트가 전제가 되면 C 가 B 의 문제(못 그림)를 풀고,
A 는 C 에서 확장성만 뺀 것이 된다. **실제로 정할 것은 "원형을 몇 개로 잡을까"이고, 그건 S3 가 실물에서 도출한다.**

### 근거로 쓰면 안 되는 것
**"재사용률 0%"는 증거가 아니다.** S1 프롬프트("둘로 보이면 둘로 남겨라")가 최대 분할을 보장했다.
0% 는 그 지시가 제대로 작동했다는 뜻이지, 블록이 기사마다 다를 수밖에 없다는 뜻이 아니다.
(PM 이 자기 지시의 산물을 세상에 대한 증거로 썼다)

### 원형 층 — 참고안. S3 가 확정한다
| 관측 타입 | 원형 | 근거 기사 |
|---|---|---|
| votes · tags_inline | 나란히 비교 | **FOMC + FTC** |
| timeline · steps | 순서 목록 | **FOMC + FTC** |
| gauge | 척도 (목표 대비 현재) | FOMC 만 |
| stats | 이름-값 | FOMC 만 |
| callout | 강조 문단 | FOMC 만 |
| examples | 순서 없는 목록 | FTC 만 |
| rule_line | 극성 목록 (✕/✓) | FTC 만 |

- 두 기사 모두에 근거가 있는 원형은 **둘뿐**이다. 나머지는 근거 1건이다.
  FINDINGS §13: "두 번째 구현체가 없을 때 설계한 인터페이스는 거의 반드시 틀린다"
- 스크루웜 브리프를 대보면 극성·순서·비교·이름-값으로 대부분 표현되고, 새로 필요한 건 지도(북상 경로)
  하나로 보인다. **슬라이드가 없어 검증은 안 됐다** (D11)

### 정규 텍스트는 비용이 아니라 요구사항이다
1. 프론트가 모르는 타입이 왔을 때
2. 스크린리더 — 게이지는 소리로 못 읽는다
3. 자유 질문(§10.6) — LLM 은 게이지를 못 본다. **텍스트 없는 블록은 질문 기능에 투명하다**
4. 공유·검색 — 카톡으로 나가는 건 텍스트다
5. **검증** — 원문 대조, entailment, 레드팀, 게이트 전부 텍스트에서 돈다. **텍스트 없는 블록은 QA 밖에 놓인다**

### 규칙
1. 모든 블록은 정규 텍스트를 가진다. 옵션이 아니다
2. 극성·순서·강조처럼 의미를 가진 표시는 정규 텍스트에 **글자로** 살아 있어야 한다
   — 근거: FTC 대조선. ✕/✓ 를 빼면 "금지하라 / 숨기지 마라"만 남아 어느 쪽이 되고 안 되는지 사라진다
3. **시각 블록은 정규 텍스트가 말하지 않는 것을 말할 수 없다**
4. 블록당 정답 표현은 하나다. 시각 데이터와 텍스트를 **둘 다 독립 저장하지 않는다.**
   따로 두면 한쪽만 고치는 순간 조용히 어긋난다(화면엔 3.4%, 질문 기능엔 3.3%).
   어느 쪽을 정답으로 할지는 S3 가 실물을 보고 정한다

### 규칙 3 이 핵심인 이유
PM 가설은 "비텍스트 블록은 정보가 아니라 모양을 더한다"였다. 대부분 맞다.
그러나 이걸 원칙으로 두면 **"모양일 뿐"이니 아무도 검사하지 않는다.**
더 위험한 건 반대 방향 — **시각이 텍스트에 없는 주장을 더하는 경우**이고, 프로토타입에 이미 있다.

| 블록 | 텍스트가 말하는 것 | 시각이 추가로 말하는 것 | 판정 |
|---|---|---|---|
| 게이지 | 2%, 3%대 | 눈금 33%·62% — "목표와 현재 사이 거리가 이만큼"이라는 비율. **위치에 근거가 없다** | **위반** |

entailment 에도 원문 대조에도 안 걸리는데, 독자 머릿속 그림은 바꾼다.
→ **게이트 3 확인 항목으로 추가.** 사람이 본다.

### 골든에 들어 있는 위반 — 게이지
입문 3장 게이지 눈금 `[33, 62]`. **S2 는 재개하지 않는다.** 고치는 방법(실제 값에서 위치 계산 /

지금 열면 관측 타입(gauge, votes …)으로 컴포넌트를 만들고 0.1b 에서 갈아엎는다.

## D15 · `resolves` 를 데이터로 두지 않는다

**상태**: DECIDED · 2026-09-21

### 불변식
```
읽기 흐름은 선형이다.
각 슬라이드의 open_question 은 바로 다음 슬라이드가 답한다.
비선형 참조는 허용하지 않는다.
```

**"허용하지 않는다"가 핵심이다.** 비선형이 필요해 보이는 상황은 슬라이드 순서가
틀렸다는 신호다. 세 장 뒤가 답해야 할 것 같으면 순서를 잘못 짠 것이지 필드가 필요한
게 아니다. §8.1 "기사 = 하나의 모험"과도 맞다. 모험은 앞으로 가지 뒤를 참조하지 않는다.

### 근거
§8.2 가 잡으려는 것은 두 가지다.

| 잡으려는 것 | 필드 없이 | 필드 있으면 |
|---|---|---|
| open_question 없는 슬라이드 (넘길 이유 없음 → 앞뒤와 합쳐야 함) | **잡힌다.** `open_question == null` | 똑같이 잡힌다 |
| 답 없이 끝나는 질문 (독자를 버려둠) | 못 잡는다 | **여전히 못 잡는다** |

`resolves: 4` 는 4번이 답했다고 **주장**할 뿐이다. 실물 20장 전부 `index+1` 이므로 그 주장은
자동 생성이고, 자동 생성된 주장을 검사하는 것은 아무것도 검사하지 않는 것이다.

**잡히는 건 필드 없이 잡히고, 필드가 필요한 건 필드로도 못 잡는다.**

### QA
1. 마지막 제외 모든 슬라이드에 `open_question` 이 있는가 — **기계 검사**
2. 다음 슬라이드가 그 질문에 실제로 답했는가 — **의미 판정. 자동화하지 않는다.**
   게이트 3(최종 검토)에 붙인다. 슬라이드를 읽으며 "여기서 왜 안 넘어가지?"를
   느끼는 것이 가장 정확하다

### 재개 조건
비선형 참조가 **정당하게** 필요한 실사례가 나오면 재논의한다.
"순서를 바꾸면 해결되는가"를 먼저 확인하고, 안 되는 경우만 해당한다.

### 기각된 안
- `resolves` 필드 — 위 근거
- 불변식을 "open_question 은 다음 슬라이드가 답한다"로만 쓰는 안 — 약하다.
  나중에 누가 `resolves` 를 다시 제안할 때 막을 근거가 없다

## D16 · `open_question` 은 teaser 에서만 나온다

## D17 · `open_question` 은 슬라이드 사이의 독립 데이터다

  슬라이드 안에 있었다. D17 은 그걸 **계약에서 어떻게 모델링하느냐**다
- D15 불변식은 그대로 성립한다. "슬라이드 N 의 open_question" 이
  "슬라이드 N 과 N+1 사이의 open_question" 으로 읽히면 된다. QA① 도 같은 뜻이 된다
- D16(teaser 만 센다)은 그대로다

세부 UI(kicker·teaser 글자 크기 등)는 프론트 레인이 열리면 도윤이 전달한다.

## D19 · 개념 문안을 고칠지 판단하는 기준

**상태**: DECIDED · 2026-09-29 · PM 결정 (도윤 위임)

### 기준
> **이 개념이 다른 기사에 재사용돼도, 독자가 틀린 그림을 갖지 않는가?**

"틀린 말인가"가 아니라 **"독자 머릿속 그림이 틀리는가"**를 묻는다.
FINDINGS §1.2 철거 테스트("나중에 더 배웠을 때 지금 배운 걸 버려야 하나?")를 Concept Atom 의 재사용 상황으로 넓힌 것이다.

- 틀린 그림을 만든다 → **고친다**
- 넓거나 느슨하지만 그림은 맞다 → **기록만 하고 두지 않는다**

### 왜 이 기준인가
1. **독자가 먼저다.** 린트는 문장을 보고, 독자는 그림을 본다. 린트에 걸려도 그림이 맞으면 독자에게 문제가 없고,
   린트를 통과해도 그림이 틀리면 문제다
2. **병목을 막는다.** "린트에 걸리면 고친다"를 원칙으로 두면 라이브러리가 커질수록 도윤의 수정 부담이 선형으로 늘어난다.
   린트 ① 이 파이프라인에 들어가면(아래) 더 그렇다

### 2026-09 린트 결과에 적용

| 개념 | 걸린 것 | 재사용 시 독자 그림 | 판정 |
|---|---|---|---|
| **C-0010** REFRESHER | "지불 의향을 추정해서" 탈락 | 명제대로면 해당 없는 것(나이로 매기는 보험료)이 해당이 된다. 경계축 기사의 **경계 개념** 자체가 넓어진다. §6.1 "규제 뉴스 최대 오독 = 범위를 넓게 읽기" | **고친다** |
| C-0010 BOUNDARY | "나에 대한 추정" | 같은 문제. 위험 추정도 "나에 대한 추정"이다. 지불 의향이 빠져 있다 | **같이 확인** |
| **C-0008** REFRESHER | "이건 방침이다" | 구속력 있는 규칙을 다루는 기사에 재사용하면 독자는 "이건 규칙이 아니다"를 믿는다. 정반대 | **고친다** |

| **C-0002** FULL ④ | 단계 전체가 현재 상태 | 물가가 목표 아래인 시기의 기사에 재사용하면 "목표보다 빠르게 오르고 있어요"가 거짓이다 | **브리지로 옮긴다** |

| C-0006 "각자" | 양화사 | 이 개념의 핵심은 인원이 아니라 **"결정이 아니라 개인 예상"**이다. "각자"가 바로 그 뜻을 전한다. 빼면 독자가 잃는 게 더 크다 | 둔다 |
| C-0002 · C-0003 REFRESHER | 긴 설명에 없는 말 | 명제에 있는 말이다. 그림이 맞다 | 둔다 (오탐) |

- 대기 표시는 **픽스처에서만** 허용한다. 발행물에는 허용하지 않는다 — 발행 불변식은 그대로

  0.1b 가 끝나면 백엔드 0.2 와 프론트가 동시에 진행된다. 0.2 를 먼저 하면 그동안 프론트가 논다
- **기술**: 대기 표시를 조용히 두면 나중에 썩는다. WARN 으로 계속 보이게 추적하면 그런 위험이 없다

### 층 판정 규칙 — 사실인지 해석인지 애매하면 해석(`claim`)으로 단다

§8.4 에 따라 독자는 "이건 원문 / 이건 Claro 의 해석" 표시를 본다.
- 해석을 사실로 달면 → 독자가 우리 추론을 1차 자료처럼 믿는다. **FINDINGS §5.2 가 가장 경계한 실수다**
- 사실을 해석으로 달면 → 조금 보수적일 뿐 독자를 속이지 않는다

그래서 판정이 갈리면 `claim` 이다. 이 규칙은 골든만이 아니라 파이프라인이 앞으로 모든 기사에 쓴다 → 계약 §6 에 넣는다.

0.1b 에 적용:
- F · DC 섞인 span — 추론이 하나라도 있으면 `claim`. refs 는 DC 만. 끊긴 F 연결은 `_` 주석으로 남긴다(0.2 가 Claim→Fact 로 옮긴다)

## D22 · D20 후속 — 이란 규칙의 범위, `Level.label` 제거

**상태**: DECIDED · 2026-09-29 · PM 판정 (도윤 위임). S3 가 게이트 반영 중 올린 두 건

### ① 이란 전쟁 규칙은 "사실을 서술한 문장"에만 적용한다

D20 은 이란 전쟁 `unsupported` 4 문장을 전부 "`fact`, refs 대기"로 정했다. **규칙을 너무 넓게 썼다** (PM 오류).
그중 입문 callout 의 "이 전쟁이 끝나면 물가는 저절로 내려갈 수도, 더 커지면 훨씬 나빠질 수도 있어요"는
사실이 아니라 **우리가 한 전망**이다. S3 가 D20 안의 두 규칙이 충돌한다고 짚었다.

- **일반 규칙이 우선한다** — 사실인지 해석인지 애매하면 `claim`. 이 문장은 애매하지도 않다. `claim` 이다
- 이란 규칙("글 그대로, `fact`, refs 대기")은 **사실을 서술한 문장에만** 적용한다
- 이 문장은 `claim`, refs 대기 — 대기 사유는 **Derived Claim 도출 필요**.
  근거 없는 사실은 출처를 채우면 되지만, **근거 없는 해석은 FINDINGS §7.2 (Derived Claim + 반증 검사)를 거쳐야 한다.**
  브리프의 DC-A~E 어디에도 없다
- 독자: 이 문장을 `fact` 로 달면 독자는 우리 전망을 원문 사실로 읽는다. D20 이 "가장 나쁘다"고 한 바로 그 경우다

### ② `Level.label` 을 뺀다. 표시 이름은 프론트가 `id` 에서 가져온다

D20 이 `id` 를 `basic` · `intermediate` · `advanced` 로 닫자 `label`("입문" · "숙련")이 `id` 에 종속됐다.
같은 것이 두 곳에 있으면 어긋날 수 있다 (S3 제안).

- **결정적 이유 — 발행된 패키지는 바뀌지 않는다 (§9.2).** 이름을 패키지에 넣으면, 나중에 "숙련"을 "심화"로 바꿀 때
  옛 기사는 옛 이름을 영원히 갖는다. 독자가 기사마다 다른 이름을 본다
- 프론트가 `id` → 표시 이름을 한 곳에서 정하면 모든 기사에서 같고, 바꿀 때 한 곳만 고친다
- 레벨이 하나인 기사는 전환 UI 를 안 그린다 — `levels.length == 1` 로 안다. `label: null` 이 하던 일은 없어도 된다

### 그 밖에 S3 가 목록 밖에서 한 것 — 수용
- `contrast` 항목의 `body` 를 선택으로 (value · body 중 하나 이상). 게이지의 글자를 그대로 두려면 필요했다
- 레벨 `id` 는 기사 안에서 겹치지 않고 basic → intermediate → advanced 순서
- `_refs_pending { until, need }` — 가짜 ID 를 refs 에 넣지 않고, 기존 발행 규칙이 그대로 막는다

## D23 · 층 판정 — "브리프를 넘어선다"를 둘로 가른다

**상태**: DECIDED · 2026-09-29 · PM 판정 (도윤 위임). 0.1b PM 검수에서

### 무엇이 틀렸나 (PM 오류 — D22 와 같은 원인)
D20 은 "`partial` 은 브리프 사실이 다 말하면 fact, **넘어서면** claim"이라고 했다.
그런데 `partial` · `unsupported` 는 S2 가 붙인 **출처 커버리지** 분류(브리프에 있다 / 일부 / 없다)다.
PM 이 이것을 **층**(사실 / 해석)에 곧바로 대응시켰다. **출처가 없는 것과 해석인 것은 다르다.**
D22(이란 규칙)도 같은 혼동이었다 — 출처(배경지식)로 묶었는데 성격이 달랐다.

### 규칙
| 문장이 하는 일 | 층 |
|---|---|
| 브리프 사실을 **바꿔 말하거나 반올림** | `fact` (그 F) |
| 브리프에 없는 **사실**을 서술 | `fact`, 대기 "Fact 출처" |
| 사실에서 **추론 · 평가 · 원인 비중**을 끌어냄 | `claim` |
| 위 셋 중 어느 것인지 애매 | `claim` (D20 원칙 유지) |

D20 의 비대칭(해석을 사실로 다는 게 더 나쁘다)은 **사실과 추론 사이가 애매할 때**의 규칙이다.
출처가 비었을 뿐인 사실은 애매하지 않다. 사건을 "Claro 의 해석"으로 달면 그것도 독자에게 틀린 그림이다.

## D1 · 기술 스택 — 프론트 (백엔드는 OPEN)

웹과 앱 **둘 다** 낸다. 둘 다 UI/UX 를 극한으로 예쁘고 부드럽게.

### 결정
**웹과 앱은 따로 만들되, 한 저장소 안에서 보이지 않는 부분만 공유한다.**

```
apps/web       Next.js (React) + Motion           — 진짜 HTML 글자
apps/app       Expo (React Native) + Reanimated   — 진짜 네이티브 제스처
packages/
  contract     ARTICLE_PACKAGE 의 TypeScript 타입 + 런타임 검증기
  core         레벨 선택 · 슬라이드 순서 등 화면 밖 로직
  tokens       색 · 글꼴 · 간격 · 애니메이션 곡선
```

- **화면 컴포넌트는 공유하지 않는다.** 한 코드로 둘 다 그리면 양쪽 다 "적당히 부드러운" 데서 멈춘다.

- **디자인 토큰은 공유한다.** 그래서 두 쪽이 같은 서비스로 느껴진다
- **웹 먼저, 앱은 그다음.** 프로토타입이 이미 HTML 이라 가장 빨리 실물이 나온다. 그리고 이 프로젝트가 아직 한 번도 못 한
  **실제 독자가 슬라이드를 읽어보는 일**(FINDINGS §12.3)이 웹 링크 하나로 가능해진다. 저장소 모양은 처음부터 위대로 잡는다

### 기각
| 안 | 이유 |
|---|---|
| Flutter (한 코드) | 애니메이션은 최상급. 그러나 **웹에서 글자를 캔버스에 그림으로 그린다** — 글자 선택 · 검색 · 스크린리더 · 공유가 약해진다. D14 가 "모든 블록에 정규 텍스트"를 정한 이유가 바로 이것들이다. 글이 본체인 Claro 와 안 맞는다 |

| 한 코드 공유 (react-native-web) | 양쪽 다 적당히 |
