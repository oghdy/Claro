## D8 · volatility 를 2값에서 3값으로

**상태**: DECIDED · 2026-09-20
**배경**: FINDINGS §5.4는 `STABLE | VOLATILE` 2값. 픽스처에 "이란 전쟁 201일째"를
넣으려 하자 둘 중 어디에도 안 맞는다는 게 드러났다.

### 결정
```
STABLE     안 변함                        3.75~4.00%
DERIVED    STABLE fact에서 계산됨          201일째
VOLATILE   조회해야만 알 수 있음           48건 → as_of 필수
```

**규칙**
1. DERIVED 는 `published_at` 기준으로만 계산한다. `now()` 재계산 금지 —
   같은 ArticlePackage 가 읽는 시점마다 다른 값을 보이면 immutable 이 아니다 (§9.2 위반)
2. 따라서 **렌더 시점 계산은 없다.** 프론트는 `value_at_authoring` 을 출력한다.
   공식은 발행 시 1회 검증용으로만 존재한다
3. `recompute(published_at) == value_at_authoring` 은 회귀 테스트가 아니라 **불변식**이다.
   안 맞으면 즉시 실패
4. 전파: 소스 중 하나라도 VOLATILE 이면 DERIVED 를 쓸 수 없다. VOLATILE 로 강등
5. 유효성("아직 진행 중인가")은 Fact 의 속성이 아니다. `storyline_ref` 가 답하고,
   §6.2 `STORYLINE_STALE` 이 이미 담당한다

### 기각된 안
- `derived_from.open_while` — `storyline_ref` 를 다른 이름으로 중복 정의한 것.
  Fact 스키마에 storyline 생명주기를 밀어넣는다
- `now()` 재계산 / 열림·닫힘에 따른 시계 분기 — immutable 위반. 복잡도 3배인데
  해결하려는 문제는 storyline 장치가 이미 풀고 있다

### 미해결로 남긴 것
- `derived_from` 의 정확한 필드 구조 → S3
- `render` 어휘의 소속 → **D12 참조. PM 추론을 전제로 넘기지 않는다**

### invalid fixture
- `volatile-missing-asof.json` (S2) · `derived-from-volatile.json` (S2)
- `merged-without-target.json` (S4) · `conflicting-alias-collapse.json` (S4)
  → 아래 둘은 CONCEPT_IDENTITY 가 없으면 쓸 수 없다. S2 에 주지 마라

### 메타
스키마를 먼저 만들었으면 마이그레이션이었을 것을, 픽스처를 쓰려다 발견했다.

## D9 · 골든 픽스처에 알려진 결함을 남기지 않는다

**상태**: DECIDED · 2026-09-20

골든 픽스처는 (a) 프론트 렌더 대상 (b) 파이프라인 diff 대상 (c) 계약 도출 원천

→ 골든은 깨끗하게. 위반 데이터는 `fixtures/invalid/` 에 별도 파일로.
→ 스키마 Task 완료 조건인 "제약 위반 데이터가 거부되는지"가 이것으로 검증된다.

## D11 · 계약은 서사축 두 개만 보고 나온다

**상태**: DECIDED · 2026-09-20

§6.1 의 서사축은 셋인데 슬라이드 프로토타입은 둘뿐이다.

| 축 | 사례 | 프로토타입 | 고유 블록 |
|---|---|---|---|
| 시간축 (델타) | FOMC | 있음 | 표결 대조 카드, 타임라인 |
| 경계축 (범위) | FTC | 있음 | `examples`(해당/비해당), `steps` |

그래도 상태축은 여전히 빈칸이다.

→ **S3 는 `ARTICLE_PACKAGE.md` 에 "상태축 블록 어휘는 미확인"을 명시적으로 적는다.**
나중에 개정이 필요하다는 걸 모르는 것보다 아는 게 낫다.

## D12 · 프론트에 렌더 시점 계산이 필요한가

**상태**: OPEN · S1 `_findings` 가 답한다

D8 에서 DERIVED 를 `published_at` 고정으로 정했다. 여기서
"렌더 시점 계산이 없다 → 프론트는 `value_at_authoring` 만 출력한다 →
`render` enum 은 프론트 어휘가 아니라 검증 함수명이다"
라는 추론이 나왔으나, **이것은 실물 없이 한 계약 설계라 채택하지 않는다.**

프론트가 정말 계산이 필요 없는지는 프로토타입을 봐야 안다. 예를 들어 숙련 뷰
타임라인이 날짜 간격을 시각적 길이로 표현한다면 프론트도 계산한다.

→ S1 프롬프트에 관찰 항목으로 넣었다. 답이 나온 뒤 S3 가 결정한다.

  간격이 길이로 전혀 표현되지 않는다. `when` 에 "9월 초"가 섞여 있어 계산 자체가 불가능하다
- stats·votes 는 전부 텍스트, 진행바는 0%/100% 이분법

**유일한 예외**: FOMC 입문 3장 gauge. `left:33%`("2%") · `left:62%`("3%대") 가
inline style 에 손으로 박힌 상수다. 축 최소·최대가 선언돼 있지 않다.
선형 가정 시 62% 는 약 3.7% 를 가리키는데 본문은 "3%대"라고만 쓴다.

→ D8 의 "프론트는 `value_at_authoring` 만 출력한다"가 실물로 뒷받침된다.
→ 다만 gauge 를 값으로 둘지 위치로 둘지는 S3 가 정한다 (FOMC-14).
  값으로 두면 그때 프론트 계산이 처음 생긴다.

## D14 · 블록 타입 — 원형 층 + 모든 블록에 정규 텍스트

**상태**: DECIDED · 2026-09-28

### 결정
골격은 닫고, 나머지는 **원형 층**에서 정의하며, **모든 블록은 정규 텍스트를 갖는다.**

처음엔 A(닫기) / B(열기) / C(골격 닫고 나머지 열되 글자 대체본 필수)의 셋 중 고르는 문제로 올렸다.
대등한 선택지가 아니었다. 정규 텍스트가 전제가 되면 C 가 B 의 문제(못 그림)를 풀고,
A 는 C 에서 확장성만 뺀 것이 된다. **실제로 정할 것은 "원형을 몇 개로 잡을까"이고, 그건 S3 가 실물에서 도출한다.**

### 근거로 쓰면 안 되는 것
**"재사용률 0%"는 증거가 아니다.** S1 프롬프트("둘로 보이면 둘로 남겨라")가 최대 분할을 보장했다.
0% 는 그 지시가 제대로 작동했다는 뜻이지, 블록이 기사마다 다를 수밖에 없다는 뜻이 아니다.
(PM 이 자기 지시의 산물을 세상에 대한 증거로 썼다)

### 원형 층 — 참고안. S3 가 확정한다
| 관측 타입 | 원형 | 근거 기사 |
|---|---|---|
| votes · tags_inline | 나란히 비교 | **FOMC + FTC** |
| timeline · steps | 순서 목록 | **FOMC + FTC** |
| gauge | 척도 (목표 대비 현재) | FOMC 만 |
| stats | 이름-값 | FOMC 만 |
| callout | 강조 문단 | FOMC 만 |
| examples | 순서 없는 목록 | FTC 만 |
| rule_line | 극성 목록 (✕/✓) | FTC 만 |

- 두 기사 모두에 근거가 있는 원형은 **둘뿐**이다. 나머지는 근거 1건이다.
  FINDINGS §13: "두 번째 구현체가 없을 때 설계한 인터페이스는 거의 반드시 틀린다"
- 스크루웜 브리프를 대보면 극성·순서·비교·이름-값으로 대부분 표현되고, 새로 필요한 건 지도(북상 경로)
  하나로 보인다. **슬라이드가 없어 검증은 안 됐다** (D11)

### 정규 텍스트는 비용이 아니라 요구사항이다
1. 프론트가 모르는 타입이 왔을 때
2. 스크린리더 — 게이지는 소리로 못 읽는다
3. 자유 질문(§10.6) — LLM 은 게이지를 못 본다. **텍스트 없는 블록은 질문 기능에 투명하다**
4. 공유·검색 — 카톡으로 나가는 건 텍스트다
5. **검증** — 원문 대조, entailment, 레드팀, 게이트 전부 텍스트에서 돈다. **텍스트 없는 블록은 QA 밖에 놓인다**

### 규칙
1. 모든 블록은 정규 텍스트를 가진다. 옵션이 아니다
2. 극성·순서·강조처럼 의미를 가진 표시는 정규 텍스트에 **글자로** 살아 있어야 한다
   — 근거: FTC 대조선. ✕/✓ 를 빼면 "금지하라 / 숨기지 마라"만 남아 어느 쪽이 되고 안 되는지 사라진다
3. **시각 블록은 정규 텍스트가 말하지 않는 것을 말할 수 없다**
4. 블록당 정답 표현은 하나다. 시각 데이터와 텍스트를 **둘 다 독립 저장하지 않는다.**
   따로 두면 한쪽만 고치는 순간 조용히 어긋난다(화면엔 3.4%, 질문 기능엔 3.3%).
   어느 쪽을 정답으로 할지는 S3 가 실물을 보고 정한다

### 규칙 3 이 핵심인 이유
PM 가설은 "비텍스트 블록은 정보가 아니라 모양을 더한다"였다. 대부분 맞다.
그러나 이걸 원칙으로 두면 **"모양일 뿐"이니 아무도 검사하지 않는다.**
더 위험한 건 반대 방향 — **시각이 텍스트에 없는 주장을 더하는 경우**이고, 프로토타입에 이미 있다.

| 블록 | 텍스트가 말하는 것 | 시각이 추가로 말하는 것 | 판정 |
|---|---|---|---|
| 게이지 | 2%, 3%대 | 눈금 33%·62% — "목표와 현재 사이 거리가 이만큼"이라는 비율. **위치에 근거가 없다** | **위반** |
| 타임라인 | 날짜 5개 | 등간격. 실제로는 9일·21일. 관례상 비례로 안 읽을 수도 있다 | 게이트 판단 |
| 수치표 | PCE 3.7% (3월 2.7%) | 빨간색 — "나쁘게 올랐다". 편집 판단이 표현에 묻혀 있다 | 게이트 판단 |

관찰은 S1·S2 가 이미 했다(FOMC-9·14·22, S2 범위 밖 #7). 그러나 전부 "프론트가 계산하느냐",
"의미냐 표시냐"로만 다뤄졌다. PM 은 D12 에서 타임라인 등간격을 **안심할 결과로** 적었다.

FINDINGS §7.8 "아직 못 잡는 것: 비유가 만드는 그림"과 **같은 범주**다. 사실 문장이 아니어서
entailment 에도 원문 대조에도 안 걸리는데, 독자 머릿속 그림은 바꾼다.
→ **게이트 3 확인 항목으로 추가.** 사람이 본다.

### 골든에 들어 있는 위반 — 게이지
입문 3장 게이지 눈금 `[33, 62]`. **S2 는 재개하지 않는다.** 고치는 방법(실제 값에서 위치 계산 /
척도를 버리고 두 값 비교로 교체)이 척도 원형을 어떻게 정의하느냐에 달려 있어서, 지금 고치면 계약을 추측하게 된다.
→ **Step 0.1b** (골든을 계약에 맞춰 재작성)에서 처리. 어느 쪽으로 고칠지는 편집 판단이라 도윤이 고른다.

D9("골든에 알려진 위반을 남기지 마라")와 긴장이 있다. 지금 골든을 읽는 건 S3 뿐이고 S3 에 명시했다.
프론트는 0.1b 전까지 열지 않는다(아래). 그래서 이 기간에 위반이 퍼질 경로가 없다.

### 순서 변경 — 프론트 레인 해제 조건 0.0b → 0.1b
원형 층으로 가면 블록 타입이 바뀌고, 블록 타입이 바뀌면 프론트 컴포넌트가 바뀐다.
"프론트는 계약이 아니라 픽스처에서 해제된다"는 **픽스처 모양이 최종이라는 전제**였다. 이제 아니다.
지금 열면 관측 타입(gauge, votes …)으로 컴포넌트를 만들고 0.1b 에서 갈아엎는다.

## D15 · `resolves` 를 데이터로 두지 않는다

**상태**: DECIDED · 2026-09-21

### 불변식
```
읽기 흐름은 선형이다.
각 슬라이드의 open_question 은 바로 다음 슬라이드가 답한다.
비선형 참조는 허용하지 않는다.
```

**"허용하지 않는다"가 핵심이다.** 비선형이 필요해 보이는 상황은 슬라이드 순서가
틀렸다는 신호다. 세 장 뒤가 답해야 할 것 같으면 순서를 잘못 짠 것이지 필드가 필요한
게 아니다. §8.1 "기사 = 하나의 모험"과도 맞다. 모험은 앞으로 가지 뒤를 참조하지 않는다.

### 근거
§8.2 가 잡으려는 것은 두 가지다.

| 잡으려는 것 | 필드 없이 | 필드 있으면 |
|---|---|---|
| open_question 없는 슬라이드 (넘길 이유 없음 → 앞뒤와 합쳐야 함) | **잡힌다.** `open_question == null` | 똑같이 잡힌다 |
| 답 없이 끝나는 질문 (독자를 버려둠) | 못 잡는다 | **여전히 못 잡는다** |

`resolves: 4` 는 4번이 답했다고 **주장**할 뿐이다. 실물 20장 전부 `index+1` 이므로 그 주장은
자동 생성이고, 자동 생성된 주장을 검사하는 것은 아무것도 검사하지 않는 것이다.

**잡히는 건 필드 없이 잡히고, 필드가 필요한 건 필드로도 못 잡는다.**

### QA
1. 마지막 제외 모든 슬라이드에 `open_question` 이 있는가 — **기계 검사**
2. 다음 슬라이드가 그 질문에 실제로 답했는가 — **의미 판정. 자동화하지 않는다.**
   게이트 3(최종 검토)에 붙인다. 슬라이드를 읽으며 "여기서 왜 안 넘어가지?"를
   느끼는 것이 가장 정확하다

### 재개 조건
비선형 참조가 **정당하게** 필요한 실사례가 나오면 재논의한다.
"순서를 바꾸면 해결되는가"를 먼저 확인하고, 안 되는 경우만 해당한다.

### 기각된 안
- `resolves` 필드 — 위 근거
- 불변식을 "open_question 은 다음 슬라이드가 답한다"로만 쓰는 안 — 약하다.
  나중에 누가 `resolves` 를 다시 제안할 때 막을 근거가 없다

## D16 · `open_question` 은 teaser 에서만 나온다

**상태**: DECIDED · 2026-09-21 · S1 FOMC-13 해소

S1 이 "한 슬라이드에 질문이 둘"인 경우를 두 건 찾았다. 정의가 없어서 둘 다 질문으로
보인 것이고, 기능이 다르다.

| | 답이 나오는 곳 | 성격 |
|---|---|---|

## D17 · `open_question` 은 슬라이드 사이의 독립 데이터다

**상태**: DECIDED · 2026-09-21 · **S3 가 계약을 쓸 때의 제약**

- D15 불변식은 그대로 성립한다. "슬라이드 N 의 open_question" 이
  "슬라이드 N 과 N+1 사이의 open_question" 으로 읽히면 된다. QA① 도 같은 뜻이 된다
- D16(teaser 만 센다)은 그대로다

세부 UI(kicker·teaser 글자 크기 등)는 프론트 레인이 열리면 도윤이 전달한다.

## D19 · 개념 문안을 고칠지 판단하는 기준

**상태**: DECIDED · 2026-09-29 · PM 결정 (도윤 위임)

### 기준
> **이 개념이 다른 기사에 재사용돼도, 독자가 틀린 그림을 갖지 않는가?**

"틀린 말인가"가 아니라 **"독자 머릿속 그림이 틀리는가"**를 묻는다.
FINDINGS §1.2 철거 테스트("나중에 더 배웠을 때 지금 배운 걸 버려야 하나?")를 Concept Atom 의 재사용 상황으로 넓힌 것이다.

- 틀린 그림을 만든다 → **고친다**
- 넓거나 느슨하지만 그림은 맞다 → **기록만 하고 두지 않는다**

### 왜 이 기준인가
1. **독자가 먼저다.** 린트는 문장을 보고, 독자는 그림을 본다. 린트에 걸려도 그림이 맞으면 독자에게 문제가 없고,
   린트를 통과해도 그림이 틀리면 문제다
2. **병목을 막는다.** "린트에 걸리면 고친다"를 원칙으로 두면 라이브러리가 커질수록 도윤의 수정 부담이 선형으로 늘어난다.
   린트 ① 이 파이프라인에 들어가면(아래) 더 그렇다

### 2026-09 린트 결과에 적용

| 개념 | 걸린 것 | 재사용 시 독자 그림 | 판정 |
|---|---|---|---|
| **C-0010** REFRESHER | "지불 의향을 추정해서" 탈락 | 명제대로면 해당 없는 것(나이로 매기는 보험료)이 해당이 된다. 경계축 기사의 **경계 개념** 자체가 넓어진다. §6.1 "규제 뉴스 최대 오독 = 범위를 넓게 읽기" | **고친다** |

## D22 · D20 후속 — 이란 규칙의 범위, `Level.label` 제거

**상태**: DECIDED · 2026-09-29 · PM 판정 (도윤 위임). S3 가 게이트 반영 중 올린 두 건

### ① 이란 전쟁 규칙은 "사실을 서술한 문장"에만 적용한다

D20 은 이란 전쟁 `unsupported` 4 문장을 전부 "`fact`, refs 대기"로 정했다. **규칙을 너무 넓게 썼다** (PM 오류).
그중 입문 callout 의 "이 전쟁이 끝나면 물가는 저절로 내려갈 수도, 더 커지면 훨씬 나빠질 수도 있어요"는
사실이 아니라 **우리가 한 전망**이다. S3 가 D20 안의 두 규칙이 충돌한다고 짚었다.

- **일반 규칙이 우선한다** — 사실인지 해석인지 애매하면 `claim`. 이 문장은 애매하지도 않다. `claim` 이다
- 이란 규칙("글 그대로, `fact`, refs 대기")은 **사실을 서술한 문장에만** 적용한다
- 이 문장은 `claim`, refs 대기 — 대기 사유는 **Derived Claim 도출 필요**.
  근거 없는 사실은 출처를 채우면 되지만, **근거 없는 해석은 FINDINGS §7.2 (Derived Claim + 반증 검사)를 거쳐야 한다.**
  브리프의 DC-A~E 어디에도 없다
- 독자: 이 문장을 `fact` 로 달면 독자는 우리 전망을 원문 사실로 읽는다. D20 이 "가장 나쁘다"고 한 바로 그 경우다

### ② `Level.label` 을 뺀다. 표시 이름은 프론트가 `id` 에서 가져온다

D20 이 `id` 를 `basic` · `intermediate` · `advanced` 로 닫자 `label`("입문" · "숙련")이 `id` 에 종속됐다.
같은 것이 두 곳에 있으면 어긋날 수 있다 (S3 제안).

- **결정적 이유 — 발행된 패키지는 바뀌지 않는다 (§9.2).** 이름을 패키지에 넣으면, 나중에 "숙련"을 "심화"로 바꿀 때
  옛 기사는 옛 이름을 영원히 갖는다. 독자가 기사마다 다른 이름을 본다
- 프론트가 `id` → 표시 이름을 한 곳에서 정하면 모든 기사에서 같고, 바꿀 때 한 곳만 고친다
- 레벨이 하나인 기사는 전환 UI 를 안 그린다 — `levels.length == 1` 로 안다. `label: null` 이 하던 일은 없어도 된다

### 그 밖에 S3 가 목록 밖에서 한 것 — 수용
- `contrast` 항목의 `body` 를 선택으로 (value · body 중 하나 이상). 게이지의 글자를 그대로 두려면 필요했다
- 레벨 `id` 는 기사 안에서 겹치지 않고 basic → intermediate → advanced 순서
- `_refs_pending { until, need }` — 가짜 ID 를 refs 에 넣지 않고, 기존 발행 규칙이 그대로 막는다

## D23 · 층 판정 — "브리프를 넘어선다"를 둘로 가른다

**상태**: DECIDED · 2026-09-29 · PM 판정 (도윤 위임). 0.1b PM 검수에서

### 무엇이 틀렸나 (PM 오류 — D22 와 같은 원인)
D20 은 "`partial` 은 브리프 사실이 다 말하면 fact, **넘어서면** claim"이라고 했다.
그런데 `partial` · `unsupported` 는 S2 가 붙인 **출처 커버리지** 분류(브리프에 있다 / 일부 / 없다)다.
PM 이 이것을 **층**(사실 / 해석)에 곧바로 대응시켰다. **출처가 없는 것과 해석인 것은 다르다.**
D22(이란 규칙)도 같은 혼동이었다 — 출처(배경지식)로 묶었는데 성격이 달랐다.

### 규칙
| 문장이 하는 일 | 층 |
|---|---|
| 브리프 사실을 **바꿔 말하거나 반올림** | `fact` (그 F) |
| 브리프에 없는 **사실**을 서술 | `fact`, 대기 "Fact 출처" |
| 사실에서 **추론 · 평가 · 원인 비중**을 끌어냄 | `claim` |
| 위 셋 중 어느 것인지 애매 | `claim` (D20 원칙 유지) |

D20 의 비대칭(해석을 사실로 다는 게 더 나쁘다)은 **사실과 추론 사이가 애매할 때**의 규칙이다.
출처가 비었을 뿐인 사실은 애매하지 않다. 사건을 "Claro 의 해석"으로 달면 그것도 독자에게 틀린 그림이다.

**상태**: 프론트 DECIDED · 2026-09-29 · 도윤 승인 (PM 추천). **백엔드 OPEN** — 0.2 DATA_MODEL 을 보고 정한다

### 전제 (도윤)
웹과 앱 **둘 다** 낸다. 둘 다 UI/UX 를 극한으로 예쁘고 부드럽게.

### 결정
**웹과 앱은 따로 만들되, 한 저장소 안에서 보이지 않는 부분만 공유한다.**

```
apps/web       Next.js (React) + Motion           — 진짜 HTML 글자
apps/app       Expo (React Native) + Reanimated   — 진짜 네이티브 제스처
packages/

  tokens       색 · 글꼴 · 간격 · 애니메이션 곡선
```

- **화면 컴포넌트는 공유하지 않는다.** 한 코드로 둘 다 그리면 양쪽 다 "적당히 부드러운" 데서 멈춘다.

- **디자인 토큰은 공유한다.** 그래서 두 쪽이 같은 서비스로 느껴진다
- **웹 먼저, 앱은 그다음.** 프로토타입이 이미 HTML 이라 가장 빨리 실물이 나온다. 그리고 이 프로젝트가 아직 한 번도 못 한
  **실제 독자가 슬라이드를 읽어보는 일**(FINDINGS §12.3)이 웹 링크 하나로 가능해진다. 저장소 모양은 처음부터 위대로 잡는다

### 기각

## D26 · 넘기는 방식 — §8.1 "세로 스크롤 스냅"과 F-2a 도윤 선택

**상태**: DECIDED · 2026-10-09 · **도윤 결정** ("지금 흐름 마음에 들어. 전체적인 큰 틀은 저렇게 가져가자" — `/lab/b5` 를 보고). F-2a 세션이 적음

### 결정 — 큰 틀은 B5 ("물음을 따라가는 여정")
처음 올린 (a) 가로 카드 / (b) 세로 스냅 **둘 다 아니다.** 탐색하면서 물음 자체가 바뀌었다 — 스크롤로 넘기지 않는다.

1. **한 번에 한 장.** 넘어가는 방법은 **물음(open_question) 버튼 하나뿐**이다. 쓸어서는 넘어가지 않는다
2. **물음 버튼은 다 읽었을 때 나온다.** 짧은 장은 화면 아래쪽에, 긴 장은 글 끝까지 내려가야
3. **누른 물음이 다음 화면으로 이어진다** — 다음 화면의 머리가 된다 (D15: slides[i+1] 이 open_questions[i] 에 답한다)
4. **위쪽 세그먼트 막대는 없다.** 장수(`3/9`)는 남긴다 — 개인화가 장수로 보인다(§8.3)는 그대로. 장수를 누르면 **지나온 길**(지나온 물음 목록)이 뜨고, 뒤로 가는 길은 그것이다. 아직 안 간 물음은 보여 주지 않는다
5. 겉모습: 다크 · 고딕 · 제목 26px · 본문 16.5px(도윤: "더 작으면 가독성이 안 좋다") · 하얀 물음 버튼
6. 층 표시: "층" 버튼으로 글자 꼬리표를 켜고 끈다 + 문장을 누르면 설명. 판단 색 없음(D20)

도윤이 말한 이유: "한 기사를 하나의 모험 · 이야기 · 여정처럼 자연스레 흐르도록 이해시키는 것. 쉽게 설명하고 질문으로 다음 내용이 자연스레 이어지게." 스토리식 막대와 옆으로 넘어가는 카드는 그 느낌이 아니라 "옆으로 슬라이드"로 읽힌다.

### 정해지지 않은 것 — F-2b 가 다듬는다
- **넘어가는 동작의 모양 · 속도는 도윤이 마음에 들어 하지 않았다.** 흐름(위 1~4)은 확정이고 움직임은 다시 만든다. "디테일은 나중에 더 예쁘게"
- 숙련(물음이 명사구)에서도 같은 느낌이 나는지 · 위와 아래에 물음이 하나씩 있는 것이 헷갈리는지 — 도윤이 아직 답하지 않았다
- 지나온 길에서 첫 장을 무엇으로 부를지(지금은 kicker) · 색 · 간격 · 토큰

### 따라오는 일
- **FINDINGS §8.1 을 고쳐야 한다** — "세로 스크롤 스냅 + 상단 세그먼트 진행바"가 확정으로 적혀 있다. 이 세션은 FINDINGS 를 고치지 않았다 → PM

## D31 추가 · 둘째 사건 — FOMC 하나로 먼저 돌린다

**상태**: DECIDED · 2026-10-09 · PM 추천, 도윤 수용 ("네가 추천하는 대로"). D31 의 나머지 항목은 OPEN 그대로

- **F-3 첫 회는 FOMC 기사 하나로 돌린다.** 두 무리 — 한쪽은 Claro, 한쪽은 같은 사건의 일반 기사. 같은 물음, 며칠 뒤 다시
- **둘째 사건은 손으로 만들지 않는다. 파이프라인 A(Phase 1)가 만든 첫 기사가 둘째 사건이다.** 그때 §13 의 엇갈린 설계로 다시 돌린다

이유
1. **독자 반응을 가장 빨리 본다.** 이 프로젝트는 실제 독자에게 한 번도 보인 적이 없다 (FINDINGS §12.3). 둘째 기사를 기다리면 그 날이 몇 주 밀린다
2. **손으로 만든 둘째 기사는 값이 비싸고 배우는 것이 적다.** FOMC 골든은 역산 → 교정 → 출처 대조 → 교정 2차까지 갔다. 같은 일을 손으로 한 번 더 하는 것은 서비스가 하려는 일(파이프라인이 만든다)이 아니다.
   파이프라인이 만든 기사를 읽혀야 "Claro 가 통하는가"를 본다 — 손으로 여러 번 고친 기사는 "공들인 기사가 통하는가"만 보여준다
3. 스크루웜 · FTC 는 골든도 1차 대조도 없고, 스크루웜 개념 3개는 이름뿐이다 (D32)

알고 가는 한계
- 사건 하나로는 "무리가 원래 달랐다"를 가를 수 없다. **첫 회의 결과는 Phase 1 게이트 판정이 아니라 첫 관찰이다.** 판정은 둘째 사건까지 돌린 뒤

## D1 추가 · 백엔드 스택

**상태**: DECIDED · 2026-10-12 · 도윤 ("백엔드 스택은 그렇게 가자"). PM 추천

| 부분 | 결정 |
|---|---|
| 언어 | **TypeScript** — 프론트와 같은 모노레포 |
| API | **Next.js 의 서버 기능 (Route Handlers)** — 웹과 같은 앱. 나중에 Expo 앱도 같은 API 를 부른다 |
| 데이터베이스 | **Postgres — Supabase** |
| 로그인 | **Supabase Auth** (나중에). 첫 독자 테스트(F-3)는 로그인 없이 독자별 링크 |
| DB 접근 | **Drizzle** — 테이블 정의가 TypeScript 라 `packages/contract` 타입과 나란히 놓인다 |
| 배포 | **Vercel** |
| 파이프라인 | 같은 저장소의 TypeScript 스크립트 + Claude API. 서버가 아니라 사람이 돌리는 반자동 도구로 시작 |

### 왜
- **계약 코드를 한 벌로.** 지금 파이썬 검사와 `packages/contract`(TS)가 같은 계약을 따로 구현한다. 백엔드가 파이썬이면 세 벌째가 생긴다. TS 면 서버가 프론트의 계약 패키지를 그대로 쓴다
- 파이프라인이 하는 일은 문서를 가져오고 · 모델에게 단계별로 시키고 · 결과를 계약대로 검사하는 것이다. 파이썬의 수치 · 학습 도구가 필요한 일이 아니다
- 독자 기록 · 교정 기록은 덧붙이기만 하는 원장이다. 패키지는 불변이라 통째로 넣는다. 지식 상태는 원장에서 다시 센다 (확정 §9.4) — Postgres 가 무난하다
- **Supabase 인 이유: 도윤이 로그인을 반드시 쓴다.** 데이터는 어느 Postgres 로든 옮길 수 있지만 계정은 옮기기 어렵다. DB 와 로그인을 한곳에서 시작한다

### 지키는 것
- **기록은 우리 API 를 거쳐서만 쓴다.** 화면에서 Supabase 로 직접 쓰지 않는다 — 계약 검사가 한 곳에서 일어나야 한다. Supabase 는 "누구인지 확인"과 "저장"만
- **원장에 계정 정보가 들어가지 않는다** (OBSERVATION §3 · D30). 어느 계정이 어느 `user_id` 인지는 원장 밖의 표 하나에만
- 기존 파이썬 검사는 그대로 둔다 — 골든을 지키는 독립된 검사다. 새 코드만 TS
- 개인화 계산이 통계적으로 무거워지면 그 계산만 따로 뗀다. 원장이 Postgres 에 있으니 어느 언어로든 읽는다

### 도윤이 할 것
Supabase 프로젝트 자리 — 안 쓰는 프로젝트를 멈추거나 지우거나 유료로. 실제 DB 가 필요해지는 것은 0.4b (API 를 배포할 때)부터다. 0.4a 는 외부 DB 없이 돈다

### 0.4b 로 넘기는 물음에 대한 PM 의 답 (세션이 실물로 뒤집을 수 있다)
- **읽는 것이 먼저다. 기록은 읽기를 막지 않는다** — 서버가 느리거나 죽어도 화면은 그대로 넘어간다. 못 보낸 사건은 쥐고 있다가 다시 보낸다. 같은 `event_id` 를 두 번 받으면 성공이다
- `seq` · `occurred_at` · `event_id` · `reading_id` · `session_id` 는 화면이 만든다. `occurred_at` 은 기기의 시각이다 (순서는 seq 가 정한다 — 계약 §5.1)
- **plan 의 `block_decisions` 는 서버가 패키지에서 계산한다.** 화면이 보낸 값을 믿지 않는다 (불변식 6 이 여기서 지켜진다). 파이썬 `derive_decisions` 와 골든에서 같은 값이 나와야 한다
- 화면은 판의 키(`article_id` · `article_version`)를 서버에서 기사를 받을 때 같이 받는다
- `user_id` 는 링크에서 온다. **대응표에 없는 `user_id` 는 기록하지 않는다 — 읽기는 된다.** 링크 없이 온 사람도 같다. 시험 경로(`/test`)는 API 를 부르지 않는다 (D33 _open-8)
- 세션 = 탭 하나 (F-3 동안의 운영 규칙. 계약의 "세션 경계 미확인"은 그대로)

- 물음(probe)의 화면과 문안은 0.4b 가 아니다 — D31 · D18 이 열려 있다

### 교훈
"데이터베이스가 지킬 수 있는 것은 데이터베이스가"를 프롬프트에 쓰면서 **무엇을 지키다 무엇을 잃는지**를 보지 않았다. 원장에서는 정합성보다 남기는 것이 먼저다. 세션이 그것을 _open 으로 올려서 잡혔다

### 차별점

| **맛** | 화면 · 움직임 · 말투 · 하나의 흐름 · "모험"은 게임 장식이 아니라 **들어가는 느낌 · 따라가는 이야기** | 따라 할 수 있다 — 위 둘과 함께여야 오래 간다 | D26 (넘기기) · 토큰 |
| 바닥 | 틀리지 않는다 — 내세우지 않는다. 가르치는 서비스라 틀린 걸 가르치면 안 된다 | | P-1 ~ W-6 · 검사는 겹으로 (D49) |

### 런칭의 시작점 (도윤: "그 전 건 만들려면 끝도 없으니 시작점을 잡을 방법")
- **시리즈마다 "지금까지의 이야기" (0화) 하나** — 과거 기사를 만들지 않고, 런칭 때 1차 자료로 과거를 한 회차로 압축한다. 그 뒤로는 회차가 쌓인다
- 처음 온 독자의 개념 지도는 빈칸이 아니라 **"이거 알아요?" 몇 번**으로 씨앗을 심는다
- 중간에 들어온 독자는 0화 + 지난 회차 요지로 따라잡는다

### 사용자에 맞게 = 조립
검증된 기사 **한 판**(사건당 비용 한 번) + 독자마다 **조립을 다르게** (아는 개념 접기 · 수준 블록 · 말투 · 페르소나는 나중). 독자마다 새로 쓰지 않는다 — 비용 (D51) · 정확성 (검증할 수 없다).
D21 (레벨 수) · D4 (개인화 범위) 는 시안을 보고 도윤이 정한다 — **독자 반응을 기다리지 않고 시안으로 먼저 느낀다** (D39 의 "독자 반응 뒤"를 여기서 푼다).
