1. **지시문 · 기록은 하루 한 장 (`logs/today/<날짜>.md`)에만** — 레인 문서 (`docs/development-*.md`)에 줄을 더하지 않는다. 매일의 일이라 레인 문서가 날마다 수백 줄 는다 · 레인 문서는 길을 바꾸는 Step 의 것이다. 매일의 커밋 접두사는 Step 이름 대신 `today <날짜>`.
2. **깨는 구절 키의 자리 = `local/<code>/meta.json`** (`breakers`) — `screen.json` 은 `screenOf` 가 모르는 칸을 빌드에서 막고 (실제 화면이 읽는 파일이다), README 는 기계가 읽기 나쁘다. 같은 파일에 `ban` (깨는 말 — 정규식 · 없어도 됨)과 `line` (목록에 적을 값 `day` · `place` · `category` · `unpromised`)을 둔다 — 미리 보기가 그 값으로 그려 **도윤이 읽은 화면 = 올라갈 화면**이 된다.
3. **짧은 이야기의 로컬 판 자리 = `local/<code>/story.json`** (긴 = `episode.json` — 파일 이름으로 가른다).
4. **이야기의 근거는 git 에 둔 문서만** (`store.documents.json`) — 파이프라인 `short.ts` 와 같은 규칙 ("캐시의 글은 쓰지 않는다"). 캐시의 글을 구절로 쓰면 `story:check` 의 구절 대조가 막는다.
5. **폰 그림은 git 밖** (`apps/web/.data/shots/<code>/`) — 한 편에 2 ~ 3MB · 날마다 두 편이면 한 달에 150MB 남짓이다. 게이트의 근거는 하루 기록의 글 (어느 그림 · 어느 글)로 남긴다.
6. **미리 보기는 검사를 못 지난 파일에도 빌드를 세우지 않는다** — 화면에 까닭을 적는다 (`lp-broken`). 미리 보기 하나 때문에 실제 화면의 배포까지 멈추면 안 된다 (실제 목록의 줄은 지금처럼 빌드를 세운다). 마른 시험에서 실제로 걸렸다 (④ 걸린 것 1).
7. **편집자는 새로 띄우고 쓰는 사람의 README · meta 를 주지 않는다** — 독자처럼 읽어야 빈 곳이 보인다 (UX-11a 가 그렇게 했다). 쓰는 사람은 **같은 서브에이전트에 이어서** 메운다 (제 글의 까닭을 안다 · UX-11b 는 새 세션이었다 — 이어서가 안 되면 새 Sonnet 에 글 + 목록).
8. **⑧ 의 e2e** — 그날 묶음에 묶인 줄만 새 묶음에 맞춰 고치고 (F-E5 가 한 방식), 그 밖에서 서면 멈춘다 (⑥ L1-a).
